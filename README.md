# Student Command Center

Personal, local-first academic & life dashboard. Built with Tauri + React + TypeScript + Rust + SQLite. Full design rationale lives in `architecture.md` at the repo root (Phase 0 doc + the companion-system amendment).

## Status

**Phase 1 — Core Application.** App shell, sidebar nav, dashboard, settings (theme + accent color, week start, all persisted), and a fully functional task manager (create/edit/complete/duplicate/delete/search/filter), all backed by real SQLite tables.

**Phase 1B — Companion Foundation.** The companion progression system is a real, wired subsystem: `companion_*` tables + seed data (one placeholder species, "Sparkling", across all 7 evolution stages), a fully deterministic Rust engine (XP, leveling, mood, evolution — no AI call anywhere in that path), a data-driven asset manifest with graceful missing-asset fallback, and a dashboard widget. Wired to real event sources as each domain lands (tasks, study/Pomodoro in Phase 2, exams in Phase 5) — see architecture.md A11 for the full event catalog.

**Phase 2 — Calendar + Pomodoro.** Day/week/month calendar views, a fully customizable Pomodoro timer (presets + arbitrary durations, persisted across navigation), and study session tracking (automatic from Pomodoro, or manual entry).

**Phase 3 — Study Analytics.** Day/week/month/year study-time charts, streaks (current + longest), daily/weekly goal tracking with companion wiring (`WeeklyGoalCompleted`/`StudyStreakReached`/`GoalMissed`/`StreakBroken`), and study time by course.

**Phase 4 — Finance.** Customizable/reorderable categories with optional monthly budgets, transactions (income/expense/saving), a deterministic monthly summary (totals, remaining balance, savings %, budget-vs-actual per category), and multi-month analytics (3/6/12-month chart + range category breakdown). Currency and monthly income baseline are configurable in Settings.

**Phase 5 — Exams.** Exam tracker with a three-state lifecycle (upcoming → awaiting result → completed/graded — a post-Phase-5 fix, since the original schema wrongly required a score at creation time), auto-calculated percentage once a result exists, deterministic analytics scoped to graded exams only (overall average, highest/lowest, average by subject, performance-over-time chart), exams shown on the Calendar, a real "Upcoming exam" Dashboard card, and companion wiring (`ExamCompleted` on first grading; `HighExamScore`/`PerfectExamScore` additionally stack on a strong result). Course/subject creation was available inline from the Exams page before the dedicated Courses page existed — see the Phase 14 entry below.

**Phase 6 — AI Infrastructure.** Provider-independent AI plumbing: Gemini (Flash/Pro) and OpenRouter providers behind one `AiProvider` trait; automatic routing (complexity → Gemini tier) or manual provider/model selection, both subject to a monthly spending limit that manual mode cannot bypass; API keys stored in the OS keychain, never in SQLite; per-request usage logging with a usage dashboard in Settings (cost shown as "unavailable" rather than fabricated when a provider doesn't report it); and a "Test AI connection" button — the one user-facing AI feature this phase ships, purely to prove the pipeline works end to end. (Local/Ollama support existed briefly during development and was permanently removed in Phase 8c — unacceptable CPU/GPU/heat cost on the developer's machine. The app is cloud-AI-only: Gemini + OpenRouter.)

**Phase 7 — AI Planner.** The first real structured-output AI feature: "Generate my day" builds a schedule from pending tasks, upcoming exams, locked/fixed commitments, and wake/sleep + focus-length preferences, with the AI's JSON response validated (shape, time ranges, task-id references, overlaps) and given one repair-retry on failure before surfacing a clear error — never silently accepting malformed output. A deterministic capacity check (plain Rust arithmetic, not AI) flags when there's more task time than available window before generation runs. Every block is fully editable — add/edit/delete/lock/mark-complete — and "Re-optimize remaining" regenerates only unlocked, not-yet-completed blocks, leaving locked and completed ones untouched. Completing a block linked to a task reuses the exact same completion path (and companion events) as the Tasks page. Schedule blocks now appear on the Calendar and as a "Today's schedule" Dashboard widget. Planner preferences (wake/sleep time, max continuous study, break length) are configurable in Settings and pre-fill each generation, editable per-request without changing the saved default.

**Phase 8 — Document System: built, then fully removed.** A complete local-first document/RAG system (PDF/DOCX/PPTX/TXT upload, extraction, local OCR via `tesseract`/`pdftoppm`, deterministic chunking, Gemini/OpenRouter embeddings with strict provider isolation, SQLite FTS5, hybrid search via Reciprocal Rank Fusion, and a RAG evidence-context assembler) was implemented across several rounds and confirmed working, including OCR on a 321-page scanned document. It was then deliberately, fully removed — migration `0017_drop_documents_system` drops every related table — in favor of pivoting to Phase 14 (future enhancements & polish, per `future_enhancement.md`) instead of continuing toward Medical AI/MCQs/Flashcards/Spaced Repetition. Migrations `0012`, `0014`, `0015`, and `0016` (which created what `0017` drops) are intentionally left in place as an accurate historical record — this project's migrations are never rewritten or deleted after the fact, only added to.

**Phase 14 — Future Enhancements & Polish (in progress).** Following `future_enhancement.md`'s own stated order. **Item 1, Data Management, done:** "Reset Saved Data" deletes user-created data (tasks, courses, subjects, exams, transactions, study/Pomodoro history, companion history, AI usage log) inside one transaction, automatically backs up the database file first (`{app data dir}/backups/reset_backup_{unix time}.sqlite`), resets the companion to its original migration-0003-seeded state rather than deleting it (the row is a singleton other code assumes always exists), and leaves Settings untouched unless explicitly opted in — in which case they're restored to schema defaults by deleting and re-inserting the singleton row, so newly-added setting columns can never drift out of sync with a hand-maintained default list. "Reset Demo Data" / "Load demo data" work off an explicit `is_demo` column (migration 0018) — never a heuristic guess at what "looks like" demo data. All three actions are in Settings → Data Management, behind explicit confirmation (type-to-confirm for the full reset).

**Item 2, Collapsible/Hover Navigation, done:** `app/Shell.tsx` — the sidebar starts collapsed (a 56px rail showing only the hamburger button), expands on hover (with a 350ms collapse delay after the pointer leaves, so moving toward a nav link doesn't clip the panel shut mid-move), and a hamburger click pins it open regardless of hover. The 56px rail is a fixed, never-resized element; the expanded panel is a separate absolutely-positioned overlay that slides in via `transform: translateX()` and floats over the main content rather than pushing it — the first version instead animated the rail's own `width`, which hit a classic flexbox bug (flex items default to `min-width: auto`, so `whitespace-nowrap` nav labels set an intrinsic minimum width that resisted shrinking back down even with `min-w-0` added). `focus-within` keeps the panel open and visible for keyboard navigation even without JS tracking focus events. `motion-reduce:` disables the transition for users with that OS accessibility preference set. Not persisted across launches (always starts collapsed) — no settings column for it yet.

**Item 3, Companion global-shell integration, done:** the companion's live state now lives at the top of the app (`App.tsx` calls `useCompanion()` once) instead of inside the Dashboard's `CompanionWidget`, and is passed down to both `Shell.tsx` and `Dashboard.tsx` — one IPC listener shared everywhere, not one per place the companion is drawn. `Shell.tsx` renders a new `FloatingCompanion.tsx` as a bottom-right corner bubble, positioned as a sibling of the nav rail and `main` rather than nested inside the nav's animated overlay panel: a CSS `transform` on an ancestor creates a new containing block for `position: fixed` descendants, so nesting it there would have silently pinned the bubble to the (usually off-screen) nav panel instead of the viewport corner. Because it's rendered outside `<Routes>`, it never unmounts or resets when navigating between pages. Clicking the bubble opens a small status popover (name, level, stage, mood, dialogue, XP/happiness bars) that closes on outside click or `Escape`; the XP/happiness bars are now a shared `CompanionStatBars.tsx` component used by both the popover and the Dashboard's detailed card, and the mood→animation-clip lookup is now a shared `moodClip.ts` (both were previously only inside `CompanionWidget.tsx`). A new `usePrefersReducedMotion.ts` hook feeds `SpriteAnimator` so its frame-stepping `setInterval` freezes on the OS's reduced-motion preference — Tailwind's `motion-reduce:`/`motion-safe:` variants (used for the bubble's own hover/pop transitions) only reach CSS, not that JS animation loop. Styling uses only the existing CSS-variable design tokens, so it's correct under light/dark theme and any custom accent color automatically. Also used the dragon reference art supplied for testing: the source JPG had a checkerboard "transparency indicator" baked into its pixels rather than real alpha, so it was cleaned up with an OpenCV flood-fill + inpaint pass and wired in as `sparkling/_devtest_dragon/sheet.png`, temporarily referenced by every stage's `idle` clip (see `assets/companions/README.md` for the full note and how to revert to the original placeholder circles).

**Item 4, Companion naming/customization, done:** Settings → Companion adds a name field (`rename_companion` command, saved on blur, propagated everywhere via the same `companion:updated` event the rest of the companion system already uses) and an "Upload a pack…" flow for replacing the companion's built-in art entirely. Picking a `.zip` via a new native file dialog (`tauri-plugin-dialog`) runs it through `custom_pack.rs`: extraction is zip-slip-protected (`enclosed_name()` rejects any entry trying to escape the target directory via `..` or an absolute path), and validation collects every problem in one pass rather than stopping at the first — wrong/missing evolution stages, a stage missing its required `idle` animation, a referenced file that's missing or isn't a valid PNG, a sprite sheet whose pixel dimensions don't match `frameWidth × frames`, or a PNG format with no alpha channel (a warning, not a rejection, since a solid background might be intentional). PNG dimension/color-type checking is a ~30-line hand-rolled IHDR-chunk reader rather than pulling in an image-decoding crate — it confirms the *format* supports transparency, not that any pixel actually is transparent, which is called out explicitly in the UI text and docs. A validated pack is copied into `{app_data_dir}/companion_packs/custom/`, registered as a `companion_species` row, and given the exact same `companion_evolution_stages` level thresholds as the built-in "sparkling" species via a new `copy_evolution_thresholds` helper — a custom pack supplies art, not a progression curve. Installing doesn't switch the active companion's appearance; a separate "Use this companion" / "Revert to default companion" pair in Settings does that explicitly, so the validation result (including warnings) can be reviewed first. Exactly one custom slot exists for now — re-uploading replaces it (item 5, Companion collection/unlocking, generalizes this to several named slots later).

The trickiest part was serving the custom pack's images at all: they live in the OS app-data directory, not under the frontend's bundled `/companions/...` static path the way built-in art does, so a plain relative URL can't reach them. `tauri.conf.json` now enables `security.assetProtocol`, scoped to `$APPDATA/companion_packs/**` (confirmed this matches the app's actual data directory: the identifier in `tauri.conf.json` and the qualifier/organization/application passed to `directories::ProjectDirs` in `db::app_data_dir()` produce the same path, so Tauri's `$APPDATA` variable and this app's own app-data helper agree — worth re-checking if either one ever changes). `SpriteAnimator` picks between the two URL schemes based on a new `SpeciesManifest.source: "bundled" | "custom"` field: bundled stays a relative `/companions/...` path exactly as before (zero behavior change for existing art), custom resolves through `convertFileSrc()` on an absolute path. `assets.rs` was refactored so both cases share one file-existence/missing-file-tracking code path (`process_raw_species`) rather than duplicating it.

Two real bugs surfaced testing this on Fayad's machine, both fixed:
1. `cargo build` failed at the build-script stage ("the `tauri` dependency features ... does not match the allowlist defined under `tauri.conf.json`") — enabling `security.assetProtocol` in the config isn't enough on its own; it also needs the `protocol-asset` Cargo feature added to the `tauri` dependency in `Cargo.toml`, or the build never even reaches compilation.
2. Custom pack sprites didn't render (bundled ones worked fine) — `SpriteAnimator` built its `background-image` as `` `url(${sheetPath})` `` unquoted. Bundled sheet paths are always plain relative strings with no special characters, so this happened to work; but `convertFileSrc()` on a custom pack's *absolute* path includes the OS app-data directory, and on macOS that's `~/Library/Application Support/...` — a literal space, which breaks an unquoted CSS `url()` value silently (no console error, the background image just never appears). Fixed by quoting it: `` `url("${sheetPath}")` ``. Worth remembering any time a file path (not just this one) gets interpolated into inline CSS.

**Phase 14 Item 8 — Secret Private Video Journal.** New `journal/` module (`crypto.rs`, `session.rs`, `storage.rs`) plus `commands/journal.rs`, isolated the same way `spotify/` is. The security shape is the whole point of this feature, so it's worth spelling out: the password itself is never stored anywhere in any recoverable form — `journal_security.password_hash` is an Argon2id PHC string, verifiable but not reversible. The actual AES-256 key that encrypts videos is *derived* from the password (Argon2id, a separate stored salt) fresh on every unlock and lives only in memory for that session (`JournalSession`, a `Mutex<Option<UnlockedState>>` managed as Tauri state) — never persisted anywhere, not even to the OS keychain, since that would make the app's own storage access the real security boundary instead of the password itself. Closing the app kills that in-memory state along with the process, so "closing the app always locks the journal" needed no extra code. Auto-lock is enforced where content actually gets decrypted (`session::get_active_key`, called first by every content-touching command), not just implied by the UI — even a frontend bug can't get a command to decrypt something past a real timeout. Repeated wrong passwords get a growing backoff (30s → 2min → 15min) rather than nothing or a permanent lock. Title and note are encrypted with the same key as the video (search decrypts in memory once unlocked, not via SQL against plaintext); videos are never SQLite BLOBs, living instead as randomly-named encrypted files under `{app_data_dir}/private_journal/videos/`. Changing the password re-encrypts every existing entry with a freshly derived key, since the key IS the password — there's no separate master key a password change could otherwise leave stale.

Secret activation is three clicks on Settings within 1.2 seconds (`app/Shell.tsx`) — pure discovery mechanism, never the security boundary. The journal renders as a full-screen overlay entirely outside React Router (no route, no URL pointing at it). Recording uses the browser's native `MediaRecorder`/`getUserMedia` — no new Tauri plugin needed. The recorded blob crosses to Rust as base64 over the normal `invoke` call rather than a temp file, a deliberate tradeoff called out explicitly: a temp-file handoff would mean briefly writing unencrypted video to disk, working against the "encrypt at rest" point for the sake of IPC efficiency. `reset_saved_data` (Item 1) now clears the journal too — entries, the password row, and the actual files on disk, plus locking any stale unlocked session — and one real bug got caught fixing that wiring: an edit had accidentally dropped the `reset_saved_data` function signature line entirely, caught by this project's after-every-edit balance check before it went any further. No journal content ever reaches `ai::` — the module imports nothing from it.

**Spotify — post-release fixes (same Phase 14 Item 6, found during real-device testing).** Four rounds of real testing on Fayad's machine surfaced issues the static verification in this sandbox couldn't catch (no way to actually call Spotify's live API here):

1. *"Unexpected response... missing field"* on every one of saved tracks/playlists/albums. Root cause was in this codebase, not Spotify: every response struct used a blanket `#[serde(rename_all = "camelCase")]`, which applies to both serializing (to the frontend — correct) and deserializing (from Spotify — wrong). Spotify's actual JSON is snake_case (`external_urls`, `display_name`), so deserialization was looking for `externalUrls` etc. and finding nothing. Fixed with serde's asymmetric form: `rename_all(serialize = "camelCase", deserialize = "snake_case")`.
2. Alongside that, playlists specifically also hit a genuine Spotify-side change: their February 2026 Web API migration renamed the playlist track-count field from `tracks` to `items`. Fixed with `#[serde(alias = "items")]`, accepting either key.
3. Clicking a track/playlist/album opened a browser tab instead of doing anything in-app. This was the original design, not a bug — but the wrong design. Every track/playlist/album is now a button that calls Spotify's Connect API directly (`spotify_play_track`/`spotify_play_context`, new `client.rs` functions), so playback is triggered from inside the app. What hasn't changed, because it structurally can't: the audio itself always comes from an already-active Spotify Connect device (phone, desktop app, speaker) — Spotify's Web API has no mechanism for a third-party app to receive playable audio directly (that's what the separate, DRM-gated Web Playback SDK is for, with uncertain support in Tauri's WebKit-based webview on macOS — not attempted here). A small "↗ Open in Spotify" icon was kept on each item for anyone who wants the external page instead.
4. Playing anything threw `Spotify returned an error (411): Length Required`. `play()`/`pause()` sent a PUT request with no body at all; reqwest's blocking client only emits `Content-Length` for an *explicitly* empty body, not a fully absent one, and Spotify's endpoint requires the header regardless. Fixed by always sending `.body("")` instead of omitting the body.
5. Podcasts didn't appear anywhere — not a bug, a genuine gap: only playlists/tracks/albums were ever built. Added `get_saved_shows` (`/me/shows`) and a fourth "Podcasts" tab, same in-app-playback treatment as everything else.
6. Opening the new Podcasts tab hit *another* "missing field" error (`publisher` this time) — confirming the pattern from #1 wasn't fully fixed by that one change, because some fields are genuinely optional/absent in Spotify's responses depending on context, not just miscased. Rather than patch each field as it's individually reported, every non-essential field (`external_urls`, `images`, `artists`, `publisher`, `total_episodes`, `duration_ms`) across all four structs (`SpotifyPlaylist`, `SpotifyAlbum`, `SpotifyTrack`, `SpotifyShow`) now has `#[serde(default)]` (or is `Option<T>`, which defaults to `None` on a missing key with plain serde — no extra annotation needed for that part specifically). Only `id`/`name` stay required, since an item with neither can't be shown or played regardless. The frontend's `externalUrls` types became nullable to match, and the "↗" link simply doesn't render when absent instead of crashing.

**Phase 14 Item 6 — Spotify Integration.** Authorization Code + PKCE (the flow Spotify requires for a distributed desktop app — no `client_secret` can be safely embedded in a binary users download), following the same "bring your own credential" pattern the Gemini/OpenRouter API keys already use: the user registers their own free Spotify app at developer.spotify.com, gets a Client ID — not a secret, it's visible in the browser URL during login, so it lives in a plain `user_settings.spotify_client_id` column (migration `0023`) rather than the keychain — and adds `http://127.0.0.1:8898/callback` as that app's redirect URI. New `spotify/` module: `pkce.rs` (verifier/S256-challenge/state generation), `oauth.rs` (opens the consent screen via `tauri-plugin-opener`, catches the redirect on a `tiny_http` loopback listener — deliberately not a full async web framework for the sole job of accepting one request — verifies the CSRF `state`, exchanges the code for tokens), `token_store.rs` (reuses `ai/keychain.rs`'s exact OS-keychain pattern — one JSON blob of access/refresh token + expiry under a single keychain entry), and `client.rs` (one thin function per Spotify Web API endpoint, no caching or business logic, so an API change stays isolated to one function). `oauth::get_valid_access_token` refreshes automatically 60s before expiry, so every command above it just asks for "a valid token" and never thinks about lifetime.

New **Spotify** nav page (playlists/saved tracks/saved albums, each linking out to Spotify rather than attempting in-app playback, plus a now-playing bar with play/pause/skip/volume when something's active) and a Settings → Spotify section for the Client ID field and Connect/Disconnect. Two honest limits documented in the UI itself rather than left to surprise someone: playback control needs Spotify Premium and an already-active device (a 404 from Spotify's player endpoints is surfaced as "no active device," not a generic error, since that's the actual common case); and "Disconnect" removes the locally-stored tokens but doesn't reach into the user's Spotify account to revoke access there — that's still a manual step on Spotify's own "Apps" settings page. No Spotify data is ever passed to `ai::router` or any `AiProvider` anywhere in this module or its callers.

**Pixel-art rendering + adjustable bubble size.** Two related asks: whether the sprite system could render pixel art (it always accepted the *file format* — PNG is PNG regardless of style — but the renderer was hardcoded to smooth/bilinear scaling, which blurs pixel art's intentionally sharp edges), and whether the floating bubble's size could be a real user preference without the companion looking "blurry or bad" at a bigger size. Both landed together because they're the same underlying issue: a bigger bubble means more upscaling, and whether that upscaling looks *good* depends entirely on the art style.

`SpeciesManifest` gained a `pixelArt: boolean` field (`manifest.json`'s `"pixelArt"`, defaults `false` via `#[serde(default)]` so every existing bundled/custom species is unaffected) that `SpriteAnimator` uses to pick `image-rendering: pixelated` (crisp nearest-neighbor) vs the existing smooth default — plumbed through `RawSpecies` → `process_raw_species` → the bundled loader, the custom-pack loader, *and* `custom_pack.rs`'s installer (`PackManifest.pixel_art` → `to_raw_species` → `RawSpeciesForWrite`, so it round-trips through `manifest.internal.json` correctly). This is genuinely why a bigger bubble doesn't have to mean blurry: for pixel art, nearest-neighbor scaling stays crisp at any size — that's the entire point of the rendering mode. For painted/illustrated art there's an honest limit no rendering trick removes: any raster image softens somewhat once displayed well past its native resolution, so a bigger bubble will show that more; higher-resolution source art is the only real fix for that, not something the renderer can paper over.

The bubble size itself is a new `companion_bubble_size_px` column on `user_settings` (migration `0022`, 48-160px range validated in Rust per the established no-CHECK-on-ALTER-ADD-COLUMN convention from migration 0009 — `commands/settings.rs`'s validation function was doing exactly this kind of check already, so it was renamed from `validate_ai_settings` to `validate_settings` rather than growing a second, oddly-named validator). A slider in Settings → Companion controls it; `Shell.tsx` threads `settings.companionBubbleSizePx` down to `FloatingCompanion`, which scales its inner `SpriteAnimator` size and fallback icon proportionally rather than just stretching the outer button — the companion's actual sprite resolution never changes, only how large the frame around it renders, exactly the "doesn't affect the companion, just the bubble" behavior asked for.

**Phase 14 Item 5 — Companion Collection.** The `companion` table was a hard singleton (`CHECK (id = 1)`) — replaced by `companion_collection` (migration `0021`): one row per owned/lockable companion, `is_unlocked`/`is_active` flags, and "exactly one active companion" enforced by a partial unique index (`CREATE UNIQUE INDEX ... WHERE is_active = 1`) rather than left to application discipline — a second simultaneously-active row is impossible to insert, not just avoided by convention. The existing companion's data migrated into slot `id = 1` unchanged (same id specifically so `companion_evolution_history`'s existing `companion_id` values, all `1` from the old hardcoded insert, stayed correct with no remapping); two more locked slots were seeded (`emberpup`, `tidewhelp`) with simple flat-color placeholder art — the same "ship the mechanism, swap in real art later" bootstrap Sparkling itself started with. `companion_evolution_history`'s foreign key had to be repointed at the new table, which meant the full SQLite-documented rebuild procedure (`CREATE ... _new`, `INSERT ... SELECT`, `DROP`, `RENAME`) migration `0008` already established as this project's pattern for that.

Every companion-touching function in `persistence.rs` became id-aware (`get_companion` → `get_active_companion` / `get_companion_by_id`; `update_companion`, `set_companion_name`, `set_companion_species`, `record_evolution` all take an explicit id now instead of assuming `1`) — six call sites across `engine.rs`, `commands/companion.rs`, and `custom_pack.rs` needed updating to match, traced with a full-repo grep before and after to make sure none were missed. `engine::process_event` now unlocks the next collection slot (`persistence::unlock_next_locked`) the instant `new_stage == "mega"` — deterministic, based on the same evolution-resolution logic that already runs every event, not a special case. Switching active companion (`switch_active_companion` command, new "Your companions" grid in Settings) is just flipping which row `is_active` — future_enhancement.md §4's "previous companion keeps its progress" and "new companion has independent XP" fall out for free once `process_event` only ever touches the active row, no explicit reset/preserve logic needed for either half.

One genuine bug this surfaced: `reset_saved_data` (Item 1) still wrote to the now-dropped `companion` table — would have broken every reset with a SQL error. Fixed to reset all 3 collection slots back to their migration-seeded state, not just one row.

**Phase 14 Item 5 prep — evolution/level-up one-shot clips, unique proud/worried art.** `mood.rs`'s `compute_mood` used to lump `LevelUp` and `EvolutionUnlocked` into one generic "celebrating" check; it now checks each separately and returns which one is actually driving it (evolution wins if both are true — it's the rarer, bigger deal, and it's what a level-up triggers in the first place). That new piece of information — `celebration_trigger: "evolution" | "level_up" | null` — is a separate nullable column (migration `0020`, no `CHECK` constraint per migration 0009's established note that `ALTER TABLE ... ADD COLUMN ... CHECK` isn't reliable on this project's SQLite version; valid values enforced in Rust instead) rather than a change to the `mood` value itself, so no existing `CHECK (mood IN (...))` constraint needed touching. `mood` still says "celebrating" for both cases, same as before; `celebrationTrigger` is what lets the frontend show the more specific `evolution`/`level_up` clip instead of the generic `celebration` fallback — `moodClip.ts`'s new `clipForCompanionState()` is the one place that logic lives, and both `CompanionWidget` and `FloatingCompanion` now call it instead of the older `clipForMood(state.mood)`. Also gave `proud` and `worried` their own clip names (`proud`, `worried`) instead of quietly reusing `happy`/`sad` — no code depends on them having art yet; SpriteAnimator's existing missing-clip fallback to `idle` covers it until real sprites exist. `assets/companions/README.md` documents the full current clip-name set for anyone drawing art, custom pack or otherwise.

**Courses tab (built alongside Phase 14, not itself in `future_enhancement.md`'s numbered list).** Full course/module (e.g. "205CNS") and subject (e.g. Anatomy, Physiology, Histology) management — add/edit/archive/delete, with `ON DELETE SET NULL` on tasks/exams that reference a deleted course/subject rather than deleting those tasks/exams too. Each subject also gets a recurring weekly class-time schedule (migration `0019`, one row per subject per day-of-week — a day with no class simply has no row) with an independent time per day, since a real timetable's times aren't constant (e.g. Anatomy at 10:00 on Saturday, 08:00 on Sunday, no class Friday). Nothing is materialized into dated calendar rows: `get_calendar_range` (backend) expands each subject's weekly template into actual occurrences for whatever date range the Calendar is showing, computed fresh via `chrono` on every call — editing a class time immediately affects every future week. Time entry uses plain `<select>` hour/minute/AM-PM dropdowns rather than a native `<input type="time">` — WebKit's native time input can visually show a complete-looking value while its actual `.value` stays empty until every internal sub-field is explicitly committed, which caused a real "Save button won't click" bug during development; selects have no equivalent failure mode.

**UI/UX modernization — Settings information architecture (Step 1 of the modernization pass).** The old Settings page was a single ~1230-line component with all 11 of its cards (General, Appearance, Study, Planner, Finance, three AI cards, Companion, Spotify, Data Management) stacked vertically on one route — functionally complete but a long scroll to find anything. Restructured into `Settings → Category → Section`: `pages/Settings.tsx` is now a compact grid of 8 category tiles (General, Appearance, AI, Companion, Spotify, Data, Privacy & Security, About — metadata in `features/settings/settingsCategories.ts`), each routing to its own page under `pages/settings/`. Every existing setting kept its exact handler logic and IPC calls — this was a reorganization, not a rewrite — mapped as follows:

- **General** — Profile (name, week start), Study goals (daily/weekly minutes), Planner defaults (wake/sleep/max-continuous/break), Finance (currency, expected income). Four originally-separate cards, kept as four cards.
- **Appearance** — Theme and Accent color, split into two cards (previously one).
- **AI** — Provider & routing (routing mode, manual provider/model, Flash/Pro/OpenRouter model names, temperature, max tokens), API & connection (API keys + status dots + "Test AI connection", moved here from the old Usage card), Limits & safety (spending limit + usage stats). This follows the AI section structure specifically called out in the modernization brief.
- **Companion** — the old page's single Companion card (name, bubble size, custom pack, collection switcher) split into four cards: Identity, Appearance, Custom companion pack, Your companions.
- **Spotify** — Connection (Client ID + connect/disconnect), unchanged, one card.

**Pass 5 — two visual fixes, and the `npm audit` triage.**

- **The stray blue line under the profile icon was a focus ring, from my accessibility work (not a feature).** On every route change the Shell moves keyboard focus to `<main>` so screen readers announce the new page. `<main>` carried the `outline-none` utility, but the global `:focus-visible { outline: 2px solid accent }` rule has the same specificity and wins depending on CSS order, so `<main>` drew a 2px accent outline. Its left, right and bottom edges sit on the window edge and are clipped, leaving only the top edge — the line. It "went away after 3–4 tab switches" because WebKit only matches `:focus-visible` on a programmatic focus under certain input histories. ## Data & backups

The SQLite file lives outside the repo, in `<per-user data folder>/com.studentcommandcenter.app` — macOS `~/Library/Application Support/…`, Windows `%APPDATA%\…`, Linux `~/.local/share/…` (or `$XDG_DATA_HOME`) — so your real data is never accidentally committed. The same folder holds journal videos, custom companion art, safety backups and `logs/scc.log` (start-up line + any crash message; first place to look if the app won't start). Every migration run backs up the previous database file (`*.sqlite.pre-migration-bak`) before applying changes.
